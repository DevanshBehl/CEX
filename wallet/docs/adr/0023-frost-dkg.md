# ADR-0023: FROST-Ed25519 distributed key generation — no trusted dealer

- **Status:** accepted
- **Date:** 2026-09-13
- **Phase:** 5
- **Amends:** ADR-0020 (retires its "interim: a trusted dealer" section), ADR-0015

## Context

ADR-0020 gave every user their own 3-of-5 FROST group, and shipped with a
known, labelled weakness: the group was created by a **trusted dealer**. The
coordinator generated all five shares, sent one to each participant, and
discarded them. For the length of that call one process held the whole key.
Compromise that host during signup and you have that user's key. The house key
was made the same way.

Everything downstream of key generation was already the right shape: the
schema, the address (the group verifying key), the signing pipeline, per-user
isolation. What needed replacing was how shares come to exist. The requirement
is absolute: **at no time may any machine, process or coordinator hold or be
able to reconstruct a group private key.**

## Decision

Per-user keys and the house key are generated by **interactive distributed key
generation**: Pedersen DKG with Feldman verifiable secret sharing and a Schnorr
proof of knowledge per participant. It runs between the five participants, and
the coordinator only moves messages. The dealer
(`frost::generate_with_dealer`, `Coordinator::provision_user_key`,
`POST /v1/frost/provision`, `POST /v1/frost/install`) is **deleted**, not
disabled.

### Protocol

The maths comes from `frost-core` 2.2 `keys::dkg`, the reference implementation
that goes with RFC 9591. We do not reimplement any of it (master-prompt rule
106). `t = 3`, `n = 5`.

| Step        | Participant `i` (on its own host, own store, own KEK)                                                                                                                                                                                                                                                                                             | Coordinator sees                              |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| **Round 1** | Samples `f_i(x) = a_{i,0} + a_{i,1}x + a_{i,2}x²`. Publishes `C_{i,k} = a_{i,k}·G` and a Schnorr PoK of `a_{i,0}`. The polynomial is sealed under the KEK **before** the commitment is returned.                                                                                                                                                  | commitments, proofs (public)                  |
| **Round 2** | Receives all five round-1 packages and checks its own is byte-identical to what it published. Verifies every PoK (`part2`). Computes the transcript hash `T_i`. For each peer `j`, evaluates `s_{i,j} = f_i(j)` and **seals** it to `j` (below). Persists the round-2 secret before returning.                                                    | four ciphertext envelopes per participant     |
| **Round 3** | Opens the four envelopes addressed to it. Each must be from the pinned sender key, for this session, key and transcript. Verifies `s_{j,i}·G == Σ_k i^k·C_{j,k}` (`part3`). Derives `s_i = Σ_j s_{j,i}` and the group package, with `Y = Σ_j C_{j,0}`. Seals `s_i` under the KEK as **pending**. Returns `Y`, `Y_i = s_i·G` and the package hash. | group key, verification shares, hash (public) |
| **Commit**  | If the coordinator's package hash equals its own, installs the pending share as _the_ share for `key_ref`. This is one SQLite transaction and never overwrites. Then wipes the session secret.                                                                                                                                                    | group key (public)                            |

Any failure after round 1 aborts the participant's session: it is marked
`aborted` and its sealed secret is set to `NULL` before the error is returned. A
forged share, a bad proof or a transcript mismatch leaves no key state behind.

### Endpoints

| Route                         | Served by   | Purpose                                                                                       |
| ----------------------------- | ----------- | --------------------------------------------------------------------------------------------- |
| `POST /v1/frost/dkg/init`     | coordinator | `{keyRef, idempotencyKey}`. Runs the ceremony; returns the address and verification metadata. |
| `POST /v1/frost/dkg/round1`   | participant | commitments + proof of knowledge                                                              |
| `POST /v1/frost/dkg/round2`   | participant | verify proofs, return sealed peer shares                                                      |
| `POST /v1/frost/dkg/finalize` | participant | open + verify shares, derive and seal pending share                                           |
| `POST /v1/frost/dkg/commit`   | participant | install the verified share                                                                    |

Every call is authenticated as the coordinator, the same as the signing rounds
(ADR-0013). `commit` is a fifth endpoint on top of the four-round description.
It exists because of the next section.

### Why a separate commit

With a single-phase finish, participant 5 refusing in round 3 would come after
participants 1–4 had already installed shares. A retry would then be refused
by those four (`share_already_installed`) for good. That is ADR-0020's split
key set by another route: an address that can never be completed. So:

1. `finalize` verifies and seals as pending.
2. The coordinator checks that **all five** reported the same group key and
   package hash. It also checks each against its **own recomputation from the
   public round-1 commitments** (`PublicKeyPackage::from_dkg_commitments`) and
   each `Y_i` against that recomputation. A participant that disagrees is not
   outvoted. The ceremony aborts.
3. Only then does `commit` run. If a commit fails partway, the coordinator
   session stays `committing` with the agreed package stored. The next `init`
   **resumes** by re-sending commits, which participants that already committed
   answer idempotently. It does not start a new ceremony.
4. The coordinator writes `frost_group_keys` (and the API writes the address
   row) only after all five commits succeed.

### Share transport: sealed peer-to-peer through the coordinator

Round-2 shares go through the coordinator, so each one is sealed from `i` to
`j`:

```
e            = fresh X25519 ephemeral key
ctx          = len-prefixed(protocol, session_id, key_ref, id_i, id_j,
                            S_i_pub, S_j_pub, e_pub, T_i)
k            = HKDF-SHA256(salt = protocol,
                           ikm  = X25519(e, S_j_pub) ‖ X25519(S_i, S_j_pub),
                           info = ctx)
envelope     = e_pub, T_i, ChaCha20-Poly1305(k, nonce = 0, aad = ctx, postcard(s_{i,j}))
```

- **Confidentiality.** Opening needs `S_j`. The coordinator holds no
  participant's static secret.
- **Sender authentication.** The static-static term `X25519(S_i, S_j)` can only
  be computed by `i` or `j`. A coordinator cannot seal a share "from `i`", even
  with a key it controls and the right transcript hash. A unit test does exactly
  that and is refused.
- **Binding.** Session id, key reference, both identifiers, all three public
  keys and the transcript hash are in both the KDF info and the AEAD associated
  data. An envelope replayed from another session, key or view does not open.
- **Fixed nonce.** Safe because every key is unique (fresh ephemeral per
  envelope). This is HPKE's single-shot pattern.
- Both DH outputs must be contributory, so a low-order peer key is rejected.

**Peer keys are pinned, never relayed.** Each participant generates its X25519
identity inside its own store, sealed under its KEK (`dkg_identity`), and
prints only the public half (`wallet-mpc dkg-identity`). Every participant is
configured with all five keys in `MPC_DKG_PEERS`. It finds **its own**
identifier by matching its own public key in that roster, and boot fails if
that disagrees with `MPC_PARTICIPANT_IDENTIFIER`. If the coordinator could
supply or swap these keys, it could stand in the middle of every share
addressed to three participants and recover the key. That is the one attack
this design must rule out.

### Round-1 broadcast: transcript binding

Pedersen DKG assumes everyone sees the same commitments. A coordinator could
**equivocate** and show participant 1 a different `C_3` than everyone else,
which would bias or break the key. Our defence costs a hash. `T_i` covers the
whole round-1 set as `i` saw it, and every envelope from `i` is AEAD-bound to
`T_i`. A recipient whose view differs cannot open it and aborts with
`dkg_transcript_mismatch`. Every pair of honest participants exchanges an
authenticated envelope, so any equivocation that affects an honest participant
is caught before a share is committed. Participants also refuse a round-1 set
that substitutes their own commitment, or that is not exactly the pinned
roster.

### Idempotency and concurrency

- `init` on a `key_ref` with a stored group returns it (`existing: true`)
  **without contacting any participant**.
- Ceremonies are serialised per `key_ref` by the coordinator's existing
  in-process lock, with every check inside the lock. Concurrent requests
  produce one ceremony and one key.
- An `idempotencyKey` is scoped to one `key_ref`. Reusing it for another key is
  refused. The API derives it as `dkg:sha256(keyRef)`, so every retry from any
  instance is the same logical request.
- Participants make every phase transition with a conditional
  `UPDATE … WHERE phase = ?`. A replayed round loses to the database and does
  not run twice. The losing request does not abort the winner's session.
- A new round 1 for a `key_ref` supersedes and wipes any unfinished session
  for that key on that participant.

### What the coordinator persists

`frost_dkg_coordinator_sessions` holds the session state and a verbatim
**transcript** of every response it received: commitments, proofs, envelopes,
verification shares. The wire types have no field that carries a share in
plaintext. The integration test
`the_coordinators_state_contains_no_private_key_material` runs a real ceremony
over sockets and reconstructs the group secret **in the test** from three
participants' sealed shares. That is the one thing the system never does. It
then searches every byte of the coordinator's SQLite file for that secret and
for each signing share, in raw, hex and base64. It also asserts that the
coordinator has no rows in any table that could hold key material.

## Threshold security, stated precisely

- **Fewer than 3 participants learn nothing about the group secret.**
  `f_i` has degree 2, so any 2 evaluations are consistent with every possible
  constant term. The group secret is `Σ a_{i,0}`, and each honest participant's
  `a_{i,0}` stays hidden. This is information-theoretic and is proven, not
  tested. The tests check what can be checked: `frost::keys::reconstruct`
  refuses below threshold, and a signature needs three participants.
- **Any 3 honest participants can sign** immediately after commit. Tested over
  sockets with three different pairs taken offline.
- **Robustness is not provided.** A malicious participant can make a ceremony
  abort, for example with a bad share or a bad proof. The log names the culprit.
  It cannot bias the key or learn anything, but it can deny service.
  Identifiable abort is enough for five operator-run hosts. A ceremony that
  aborts repeatedly because of one participant is an incident, handled in the
  [participant loss](../runbooks/participant-loss.md) runbook.
- **Key bias.** Plain Pedersen DKG lets a rushing adversary slightly bias the
  distribution of `Y`. It cannot choose `Y` or learn its discrete log. FROST's
  security proofs account for this, and it is accepted.

## Alternatives considered

**Keep the dealer, harden the coordinator host.** Rejected. It cannot meet the
requirement at all. A dealer holds the key by construction, and no amount of
host hardening turns "briefly holds the key" into "never holds the key".

**HPKE crate (RFC 9180) instead of the composed X25519/HKDF/ChaCha20-Poly1305.**
This was close. HPKE auth mode gives the same properties with a standardised
encoding. We did not choose it because the Rust HPKE crates have seen less
review than `x25519-dalek`, `hkdf` and `chacha20poly1305`, which are all
RustSec / dalek maintained. The construction here is HPKE's auth-mode key
schedule in simplified form, and nothing is composed below the AEAD. Revisit if
a widely reviewed HPKE crate becomes standard in this dependency tree.

**Coordinator-relayed peer keys, with participants signing their own keys under
an identity key.** This moves the pinning problem instead of removing it:
participants would still need to pin the identity keys. Pinning the transport
keys directly means one fewer key type.

**A real broadcast channel (a bulletin board or consensus) for round 1.** It
has stronger liveness properties, but it is a new distributed component.
Transcript binding gives the safety property (no silent equivocation) at the
cost of an abort. With five operator-run hosts, that trade is correct.

**Single-phase finish.** It is simpler, and the split-key failure it causes is
described above. Rejected.

## Consequences

- **The trusted-dealer caveat is retired** from ADR-0020, the threat model and
  the README. No code path generates more than one share of a group.
- **Operators have one new setup step.** Collect each participant's
  `wallet-mpc dkg-identity` and distribute `MPC_DKG_PEERS` to all five. Changing
  a participant's host or KEK changes nothing about its identity: the identity
  lives in its store. Replacing a participant's store does change the identity,
  and every peer's roster must then be updated.
- **Existing keys are unaffected.** Shares made by the dealer before this change
  keep working, because `frost_shares` has the same format. They are still
  **dealer-made**: whoever controlled the coordinator at their creation could
  have kept them. Deployments that created user or house keys before this ADR
  should treat those keys as dealer-exposed and move funds to DKG-generated
  keys. Devnet keys made during ADR-0020's verification fall into this group.
- **A signup costs one ceremony.** About 20 authenticated HTTP calls. Measured
  at about 20 ms on loopback across five local processes. ADR-0020's cost
  statement already assumed a DKG round per user.
- **Not yet done:** an operator-facing command to list or clear aborted
  sessions (`Store::latest_dkg_session` exists for diagnosis). Resharing and
  repair are still per-user, as ADR-0020 records.
