# ADR-0020: Segregated custody — per-user addresses, per-user keys, no omnibus

- **Status:** accepted
- **Date:** 2026-09-12
- **Phase:** 5
- **Supersedes:** ADR-0005 (deposit keys as a lower-privilege class)
- **Amends:** ADR-0004 (deposit address model), ADR-0017 (sweep policy)

## Context

The system built through Phase 4 is an **omnibus** custodian: users have their
own deposit addresses, but funds are swept into a pooled hot wallet and the
ledger tracks one `chain_assets` account per asset with no owner. That is how
an exchange works, and it has two properties an institutional custodian cannot
accept:

- **Commingling.** One user's funds are indistinguishable on-chain from
  another's. In an insolvency there is no per-customer claim to a specific
  on-chain balance, only a claim against a pool.
- **Shared blast radius.** A treasury compromise loses everyone's funds at once.

The requirement is **segregated custody**: every user holds their own isolated
on-chain address and their own Associated Token Accounts, funds never pool, and
each user's balance is reconcilable against a specific address.

## Decision

### 1. `chain_assets` is partitioned per owner

The chart of accounts already keys on `(owner_id, asset, type)`. Today
`chain_assets` uses `owner_id = NULL` — one pooled account per asset. It becomes
per-user:

```
chain_assets  owner_id = <user>   what THIS user's address holds on-chain
chain_assets  owner_id = NULL     house-owned: fee wallet, nonce rent
```

A deposit becomes `debit chain_assets:{user} / credit user_available:{user}` —
both sides of the entry now name the same user, and the invariant that makes
segregation real is that those two projections must agree per user, not in
aggregate.

### 2. No sweeps

The sweep pipeline is disabled. Funds stay where they land. ADR-0017 built
sweeps for the omnibus model; under segregation a sweep would be the act of
commingling, which is the thing being ruled out. The planning code and its
accounting are retained but unwired, because rebalancing between _house_ tiers
is still a real future need and its ledger semantics were the hard part.

### 3. Withdrawals originate from the user's own address

The source of a withdrawal transaction is the user's segregated address. The
**fee payer remains the house**, so the user needs no SOL to move a token — a
gasless experience that is also the only way a token-only balance is spendable.

That makes a withdrawal a **two-signer transaction**: the house fee payer, and
the user's segregated key.

### 4. Per-user keys under 3-of-5 FROST, generated by real DKG

This is the decision that costs the most and matters the most.

**The problem segregation creates.** ADR-0005 allowed deposit keys weaker
protection — encrypted at rest, single signer — on one specific ground: a
deposit key could send to _one hardcoded destination and nowhere else_, so
compromising one yielded a single user's balance between sweeps and could not
redirect it anywhere the platform did not already control.

Under segregation that justification is gone. A user's key must pay arbitrary
destinations, so every user key is now a full-privilege key. Deriving them all
from one `DEPOSIT_SEED` in the API process would replace _one treasury behind
3-of-5 threshold signing_ with _N full-privilege keys behind a single hot
secret_ — **strictly weaker than the omnibus model it replaces**, and the exact
opposite of the intent.

**So each user's address is its own 3-of-5 FROST group**, created by a real
distributed key generation round at address creation. No machine ever holds a
whole key; no single secret governs more than one user.

**The address is the group verifying key.** It is not derived from a seed at an
index (ADR-0004), because there is no seed. `DEPOSIT_SEED` becomes vestigial for
new addresses.

### Interim: a trusted dealer, behind the same interface

The DKG ceremony is interactive and is the last thing being built. Until it
lands, per-user groups are created by the **trusted dealer** already used for
the house key: the coordinator generates all five shares, distributes one to
each participant, and discards them.

This is honestly weaker than DKG and is labelled as such — the coordinator
process briefly holds the whole key, so a compromise of that host at the moment
of provisioning yields that user's key. It is accepted only as a sequencing
decision, because everything downstream of it is identical either way: the
schema, the address, the signing pipeline, and the per-user isolation are the
shape they will keep. Swapping the dealer for DKG changes `provision_user_key`
and nothing else. Every provisioning logs a warning saying so.

Three properties are enforced regardless of how the shares are generated:

- **Distribute before recording.** Shares go to all five participants before the
  coordinator stores the group's public package. The safe failure is a user with
  no address, not an address nobody can sign for.
- **Never overwrite a share.** A participant refuses an install for a `key_ref`
  it already holds. A retried provisioning is the coordinator's problem to
  resolve; silently replacing a share is how a funded address becomes
  unspendable.
- **Match shares to the roster by identifier, not by position.** Round 2 selects
  signers by the roster's identifier, so a share delivered to the wrong host
  would aggregate to nothing. Zipping the two lists would have made correctness
  depend on the order of an environment variable.

### The coordinator authenticates to participants

Participants authenticate every caller (ADR-0013), and a participant's only
legitimate caller is the coordinator — so the coordinator holds an Ed25519 key
of its own (`MPC_COORDINATOR_KEY`), and each participant's
`MPC_CALLER_PUBLIC_KEY` is its public half. It signs the same canonical request
string everything else does; it cannot sign transactions, only requests.

This was discovered by the first test that ran a real coordinator against real
sockets. Every earlier threshold test played the coordinator itself, in test
code that signed correctly, so the coordinator's own unsigned requests were
never exercised — the rounds would have failed with `401` on the first
withdrawal of a real deployment. It is the same failure shape recorded elsewhere
in this repo: a green test that proves something other than what ships.

### What this costs, stated plainly

- **A DKG round per user.** Three rounds of messages between five participants
  at signup. ADR-0005 rejected this for a consumer exchange — "a DKG round per
  user is not a thing that scales" — and that objection still stands at consumer
  volumes. It is accepted here because institutional custody means fewer,
  larger accounts, and because the alternative is a single hot seed governing
  every customer.
- **5× key storage**, one share per participant per user.
- **Address creation becomes a distributed operation that can fail.** It is no
  longer a pure function of a seed and an index, so it needs its own
  idempotency, its own retry path, and its own failure state.
- **Recovery is per user.** Losing a participant means resharing for every user
  it held a share of, not once.

### What it buys

- No single secret governs more than one user.
- A compromise of any three participants for _one_ user yields _one_ user's
  funds — not the platform's.
- The master-seed risk recorded in the threat model disappears rather than
  growing.

### Verified on devnet

The whole path was exercised against live devnet, which is the only thing that
settles whether it works:

- The coordinator provisioned a per-user 3-of-5 group; the address IS the group
  verifying key, and the stored derivation path reads `frost:3-of-5:user:{id}`
  rather than a BIP-32 path, because there is no seed.
- A withdrawal produced a transaction with **two signatures**: the house as fee
  payer and nonce authority, the user's own group as the source. Both came from
  3-of-5 rounds; participants 4 and 5 were never asked.
- The ledger moved `user_available → user_locked → chain_assets:{owner}`, and
  that owner's `chain_assets` total equalled the address's on-chain balance
  exactly.

Three things only a live run surfaced, all now fixed and pinned by tests:

1. **Provisioning was not concurrency-safe.** Two simultaneous requests for one
   `key_ref` both saw "no key" — the group package is recorded only after all
   five installs — and both generated a complete share set. One was refused by
   the first participant it reached. Raced the other way it would have produced
   a SPLIT KEY SET: an address that receives deposits and can never spend them.
   Provisioning is now serialised per `key_ref` with the idempotency check
   inside the lock.
2. **A coordinator needed a SHARE to boot.** It read the house group from
   `frost_shares`, so it could not start until someone handed it key material —
   contradicting the one property a coordinator has. It reads the public
   package from `frost_group_keys` now, and provisions the house key on first
   boot like any other.
3. **Workers claimed by status alone.** `claimNext` did not filter on `chain`,
   so one cluster's worker would claim another cluster's withdrawal, lease the
   wrong nonce pool and ask the wrong RPC. See ADR-0021.

## Alternatives considered

**Seed behind the MPC boundary.** Move `DEPOSIT_SEED` into `services/mpc` and
derive-and-sign inside it. Far cheaper, and a real improvement on the status quo
— the API could request a signature but never read the seed. Rejected because
one secret would still govern every user's funds, and an attacker who reaches
the signing service reaches all of it. It is the right answer for a consumer
product and the wrong one here.

**Keep the seed in the API.** Fastest. Rejected: it makes the segregation purely
an accounting fiction. On-chain the funds are separate; in terms of key
compromise they are not separate at all, and describing that as "segregated
custody" to an institutional counterparty would be misleading.

**HSM-backed derivation.** What many real custodians do. Out of scope for a
project with no hardware, and it reintroduces a single master secret protected
by a single device.

## Consequences

- **ADR-0005 is superseded.** There is no longer a lower-privilege key class.
- **ADR-0004 is amended**: addresses come from DKG, not from a derivation path.
  Existing derived addresses keep working and keep their history; new ones do
  not use the seed.
- **Reconciliation becomes per user** (ADR-0021 covers the cluster axis). The
  aggregate comparison is no longer sufficient: a total that matches while two
  users' balances are individually wrong is exactly the failure segregation
  exists to prevent.
- **Rent is sponsored by the house.** Creating a user's address and their ATAs
  costs lamports the user did not deposit. It is debited from `house_rent` and
  never charged to the user, who cannot withdraw it either.
- **Signup gets slower and can fail.** The DKG round is on the path to a usable
  address, and that is a user-visible latency and failure mode that did not
  exist before.
- **This is unaudited.** Per-user threshold custody is more moving parts than
  the model it replaces, and more moving parts is not automatically safer.
  Master-prompt rule 8 applies in full.
